# TermDeck v1.6.0

## 修复

**SFTP 下载慢到几乎不动**

根因是传输方式，不是网络：ssh2 的读流（以及 `fastGet`）是**一次只发一个读请求**，等回来再发下一个。
于是速度 = 块大小 ÷ 往返时间 —— 用 32 KB 和 70 ms 往返算，就是 **0.5 MB/s 左右**；往返 200–300 ms 的
远端（"别的工具 10 MB/s"的环境）算下来只剩 **0.13 MB/s**，也就是"半天不动"。

现在传输改成**固定并发、始终有多个块在飞**：128 KB × 16 = 2 MB 在途。同一个文件、同样的线路，
速度不再由往返时间决定。

- 下载与上传都改了（上传原来是 2.2 MB/s，现在 3.5 MB/s 左右，同样受益）。
- **取消仍然是真的取消**：中止后不再申请新块，最多等当前在途的那一批（实测 32 块里读了 16 块就停），
  不会出现"取消了但还在往下拉 4 GB"。
- 块按自己的偏移写入，不会因为完成顺序不同而把文件写乱。

**为什么本机测不出你那个数字**：我用真实主机（82.156.226.192）测了 16 MB —— 上传 2.2 MB/s、下载 0.46 MB/s。
然后对比各种策略：顺序 32K / 64K / 256K / 1M、`fastGet` 并发 64，**全部都是 0.46 MB/s**；再用系统自带的
`scp` 拉同一个文件，**也是 34.8 秒 / 0.46 MB/s**。也就是说这条测试线路的下载方向本身被限速在
0.46 MB/s，任何客户端都一样 —— 在它上面测不出改进，也不该假装测得出。

## 新增

**把文件拖到 SFTP 面板上即可上传**

- 拖进面板时整块列表会高亮并提示"松手即上传到这个目录"，放下就传，进度照旧显示在快捷指令上方的传输栏里。
- 支持一次拖多个（按顺序传，避免挤在一个 SFTP 通道里互相排队）。
- 既能拿到 `File` 的真实路径（Electron 32+ 用 `webUtils.getPathForFile`），也能读 `text/uri-list` /
  `text/plain` 里的路径 —— 从资源管理器、其他文件管理器拖过来都能用；读不出来的内容会明确说一声，
  而不是静默失败。

## 验证

完整闸门 `npm run verify`：41 套件全过。`smoke:drawer` 114 → **123 条**：

- **并发是真的**：用一个"每次请求都延迟 20 ms"的替身 SFTP 传 32 个块 —— 顺序实现至少要 640 ms，
  实测 **155 ms**（下载）、**127 ms**（上传）。这条断言在旧实现上必然失败，而它不依赖网络速度。
- 32/32 块、文件大小 4 MB 一致 —— 并发没有把文件写乱或漏块。
- 中止后只读了 **16/32** 块 —— 取消不再"取消了个寂寞"。
- 拖拽：悬停时出现提示、放下后文件真的出现在远端目录里、提示消失。
